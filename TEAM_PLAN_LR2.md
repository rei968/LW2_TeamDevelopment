# План виконання ЛР2: Колективна розробка додатків із використанням Git
## Проєкт: Платформа для онлайн-торгівлі (E-Commerce Platform)

---

## 1. Стек технологій та Архітектура

| Рівень | Технології | Опис |
| :--- | :--- | :--- |
| **Backend** | ASP.NET Core Web API (.NET 8/9) | REST API, маршрутизація, валідація, фільтрація, бізнес-логіка |
| **Frontend** | Blazor WebAssembly + MudBlazor | Клієнтський SPA, Material UI компоненти (таблиці, діалоги, форми) |
| **Спільний код** | Shared Class Library | DTO, Enums, моделі запитів/відповідей для уникнення дублювання C# |
| **База даних** | Entity Framework Core + SQLite | Автономна локальна БД у файлі `shop.db`, міграції через EF Core |
| **Безпека** | ASP.NET Core Identity + JWT | Рольова автентифікація (`Admin`, `Customer`), захист ендпоінтів та сторінок |
| **Real-time** | SignalR | Оновлення статусів замовлень та залишків на складі в реальному часі |
| **Тестування** | xUnit + FluentAssertions + Moq | Юніт-тести сервісів, перевірки кошика, розрахунків і валідації |

### Структура Solution (`Shop.sln`):
```text
Shop.sln
├── src/
│   ├── Shop.Api/          # ASP.NET Core Web API, EF Core DbContext, Controllers, Hubs
│   ├── Shop.Client/       # Blazor WebAssembly, Сторінки клієнта, Адмін-панель, MudBlazor
│   └── Shop.Shared/       # Спільні DTO, Enums, інтерфейси, моделі валідації
├── tests/
│   └── Shop.Tests/        # xUnit тести бізнес-логіки та сервісів
└── docs/
    ├── TESTING.md         # Тест-план, чеклісти перевірок та баг-репорти (Ілля)
    └── GIT_WORKFLOW.md    # Інструкція з гілок, комітів та вирішення конфліктів
```

## 3. Git Workflow для лабораторної роботи

### Стратегія галуження (GitHub Flow):
* `main` — стабільна релізна гілка (захищена, прямий пуш заборонений).
* `develop` — інтеграційна гілка для розробки.
* `feature/<ім'я>-<назва_задачі>` — індивідуальні робочі гілки студентів.

### Порядок роботи:
1. Студент створює гілку від `develop`:
   ```bash
   git checkout develop
   git pull origin develop
   git checkout -b feature/lyosha-cart-checkout
   ```
2. Робить осмислені комміти за стандартом **Conventional Commits**:
   - `feat: додав логіку зміни кількості товару в кошику`
   - `fix: виправлено округлення підсумкової ціни`
   - `test: додано юніт-тести перевірки залишків товару`
   - `docs: описано баг-репорт #3 по фільтрації`
3. Створює **Pull Request (PR)** у гілку `develop`.
4. Тімлід (Же) проводить Code Review, залишає зауваження або ставить `Approve` і робить `Merge`.

## 4. Спеціальний сценарій: Демонстрація та вирішення Merge Conflict

Для відмінного захисту лабораторної роботи викладачі вимагають показати практичне вирішення merge-конфлікту в Git.

### Сценарій:
1. **Же** та **Ярік** створюють дві паралельні гілки від `develop`:
   - Же: `feature/zhe-order-status`
   - Ярік: `feature/yarik-order-discount`
2. Обидва розробники редагують один і той самий файл: `src/Shop.Shared/DTOs/OrderDto.cs` (наприклад, змінюють властивість `public decimal TotalAmount { get; set; }` або додають розрахунковий метод).
3. **Же** першим завершує задачу, відкриває PR і зливає його в `develop`.
4. **Ярік** намагається оновити свою гілку з `develop`:
   ```bash
   git checkout feature/yarik-order-discount
   git merge develop
   # АБО git pull origin develop
   ```
5. **Git фіксує конфлікт** у файлі `OrderDto.cs` (з'являються маркери `<<<<<<< HEAD`, `=======`, `>>>>>>>`).
6. **Ярік** відкриває Visual Studio / VS Code, викликає Merge Tool, узгоджує з Же фінальний вигляд коду, зберігає файл.
7. Завершення злиття та фіксація комміту:
   ```bash
   git add src/Shop.Shared/DTOs/OrderDto.cs
   git commit -m "fix(merge): вирішено конфлікт у OrderDto між знижками та статусом"
   git push origin feature/yarik-order-discount
   ```
8. *Скріншоти конфлікту, маркерів та вирішення додаються до звіту лабораторної роботи!*
