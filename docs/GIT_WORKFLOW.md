# 🌿 Git Workflow: Інструкція для команди

Цей документ описує стандарти роботи з репозиторієм для виконання лабораторної роботи №2 з колективної розробки додатків.

---

## 1. Структура гілок

| Гілка | Призначення | Хто має доступ на запис |
| :--- | :--- | :--- |
| `main` | Релізна стабільна версія. Прямий `push` заборонено! | Тільки злиття PR з `develop` після релізу |
| `develop` | Головна робоча гілка проєкту. Всі фічі зливаються сюди. | Через Pull Request з рев'ю Тімліда |
| `feature/*` | Робоча гілка студента для конкретної задачі. | Автор задачі |

---

## 2. Покроковий цикл розробки фічі

### Крок 1. Оновлення та створення гілки
Завжди починайте нову задачу від актуального стану гілки `develop`:
```bash
git checkout develop
git pull origin develop
git checkout -b feature/ім_я-коротка_назва
```
*Приклади назв гілок:*
- `feature/zhe-auth-identity`
- `feature/yarik-products-api`
- `feature/lyosha-cart-ui`
- `feature/illia-unit-tests`

### Крок 2. Написання коду та комміти
Кожен коміт має бути атомарним і мати зрозуміле повідомлення за стандартом **Conventional Commits**:
- `feat:` нова функціональність
- `fix:` виправлення помилки
- `test:` додавання або зміна тестів
- `docs:` зміни в документації або звітах
- `refactor:` рефакторинг коду без зміни функціональності
- `chore:` оновлення конфігурацій, пакетів тощо

*Приклад комміту:*
```bash
git add .
git commit -m "feat: додано фільтрацію товарів за ціновим діапазоном"
```

### Крок 3. Підготовка до злиття (Синхронізація з develop)
Перед створенням PR перевірте, чи не з'явилися нові зміни в `develop`:
```bash
git checkout develop
git pull origin develop
git checkout feature/ім_я-коротка_назва
git merge develop
```
Якщо виникли конфлікти — вирішіть їх локально, перевірте працездатність збірки проєкту (`dotnet build`) і закоммітьте результат.

### Крок 4. Відправка гілки на GitHub
```bash
git push -u origin feature/ім_я-коротка_назва
```

### Крок 5. Створення Pull Request (PR)
1. Відкрийте репозиторій на GitHub.
2. Натисніть **Compare & pull request**.
3. Вкажіть цільову гілку (base): `develop`.
4. Заповніть опис PR: що було зроблено, як протестувати.
5. Призначте рев'юера: Тімліда (`@rei968`) або колегу по стеку.
6. Після успішного рев'ю (`Approve`) Тімлід виконує **Squash and merge** або звичайний **Merge**.

## 3. Демонстрація та вирішення Merge Conflict (для викладача)

У ході лабораторної роботи обов'язково демонструється сценарій штучного або реального конфлікту злиття.

### Як це працює:
1. Двоє розробників (наприклад, Же та Ярік) змінюють один і той самий рядок у файлі `src/Shop.Shared/DTOs/OrderDto.cs` у різних гілках.
2. Перший розробник зливає свій PR у `develop`.
3. Другий розробник робить `git merge develop` у свою гілку і отримує статус:
   ```text
   CONFLICT (content): Merge conflict in src/Shop.Shared/DTOs/OrderDto.cs
   Automatic merge failed; fix conflicts and then commit the result.
   ```
4. У файлі з'являються маркери конфлікту:
   ```csharp
   <<<<<<< HEAD
   // Варіант Яріка
   =======
   // Варіант Же з develop
   >>>>>>> develop
   ```
5. Розробники спільно обирають компромісний варіант, видаляють маркери, зберігають файл.
6. Фіксація вирішення:
   ```bash
   git add src/Shop.Shared/DTOs/OrderDto.cs
   git commit -m "fix(merge): вирішено конфлікт у OrderDto"
   git push origin feature/...
   ```
7. Зробіть скріншоти конфлікту та його вирішення для включення у звіт!
