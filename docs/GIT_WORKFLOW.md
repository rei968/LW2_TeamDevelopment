# 🌿 Інструкція з Git-Workflow та сценарій Merge Conflict
> **Лабораторна робота №2:** Командна розробка додатків із використанням Git  
> **Проєкт:** CineSphere 🎬

---

## 📌 1. Модель розгалуження (Git Flow)

Проєкт використовує адаптовану модель розгалуження **Git Flow**, що забезпечує стабільність релізної версії та паралельну розробку:

```text
main (реліз v1.0.0-cinesphere)
  │
develop (інтеграційна гілка) ────────────┬──────────────────┬───────────► [Реліз]
  │                                     │                  │
  ├── feature/zhe-catalog-ui ───────────┤ (Merge via PR)   │
  ├── feature/yarik-booking-logic ──────┘                  │
  ├── feature/lyosha-hall-ui ──────────────────────────────┤ (Merge via PR)
  └── feature/illia-qa-tests ──────────────────────────────┘
```

- **`main`** — захищена виробнича гілка. Містить тільки повністю протестований та готовий до показу код. Прямі коміти заборонені.
- **`develop`** — основна робоча гілка команди. Сюди зливаються всі розроблені фічі через Pull Requests.
- **`feature/*`** — персональні гілки кожного студента для роботи над своїми завданнями. Назва гілки має формат: `feature/ім'я-коротка_назва`.

## 📝 2. Стандарт повідомлень комітів (Conventional Commits)

Всі коміти повинні бути змістовними та відповідати загальноприйнятому стандарту:

| Префікс | Коли використовується | Приклад |
| :--- | :--- | :--- |
| `feat:` | Додавання нового функціоналу | `feat(hall): додано неонове підсвічування обраних сидінь` |
| `fix:` | Виправлення помилки / бага | `fix(pricing): виправлено округлення суми зі студентською знижкою` |
| `test:` | Додавання або зміна тестів | `test(qa): додано автотест валідації номеру телефону` |
| `docs:` | Оновлення документації | `docs: оновлено інструкції для команди у TEAM_PLAN_LR2.md` |
| `style:` | Форматування коду, відступи (без зміни логіки) | `style(css): оптимізовано правила медіа-запитів для мобілок` |
| `chore:` | Допоміжні зміни, конфігурація | `chore: оновлено .gitignore` |

## ⚡ 3. Базові команди Git для розробника

### Початок роботи (Оновлення develop та створення гілки):
```bash
# 1. Переходимо в develop
git checkout develop

# 2. Підтягуємо свіжі зміни з віддаленого сервера
git pull origin develop

# 3. Створюємо власну гілку і переходимо в неї
git checkout -b feature/ваше_ім_я-назва_задачі
```

### Фіксація та публікація змін:
```bash
# 1. Перевірити, які файли були змінені
git status

# 2. Додати файли до індексу
git add .

# 3. Зробити коміт
git commit -m "feat(ui): опис виконаної роботи"

# 4. Відправити гілку на GitHub (перший раз з -u)
git push -u origin feature/ваше_ім_я-назва_задачі
```

## 💥 4. Покроковий сценарій створення та вирішення Merge Conflict

Вимогою лабораторної роботи є демонстрація викладачу **вміння свідомо вирішувати конфлікти злиття (Merge Conflict)**.

### 🎯 Місце конфлікту:
Файл бізнес-логіки `js/pricing.js`, функція `calculateOrderTotal` (розрахунок підсумкової вартості замовлення зі знижками).

---

### 🎬 Сценарій симуляції конфлікту:

#### Крок 1. Розробник А (Ярік) вносить зміни
Ярік створює гілку `feature/yarik-vip-discount` і додає **VIP-знижку 10%**:
```javascript
// js/pricing.js у функції calculateOrderTotal
if (hasVipSeats) {
  discountRate = 0.10; // Знижка 10% для поціновувачів комфорту (Ярік)
}
```
Ярік комітить та пушить свою гілку:
```bash
git checkout -b feature/yarik-vip-discount
git add js/pricing.js
git commit -m "feat(pricing): додано знижку 10% на замовлення з VIP-місцями"
git push -u origin feature/yarik-vip-discount
```
Ярік робить PR на GitHub у `develop` $\rightarrow$ Тімлід схвалює його і робить **Merge**. Зміни опиняються в `develop`.

---

#### Крок 2. Розробник Б (Же) змінює той самий блок коду
Тим часом Же у своїй паралельній гілці `feature/zhe-bulk-discount` змінює **ті самі рядки**, але додає **групову знижку 15% на 3+ квитків**:
```javascript
// js/pricing.js у функції calculateOrderTotal
if (seats.length >= 3) {
  discountRate = 0.15; // Групова знижка 15% для компаній від 3 осіб (Же)
}
```
Же комітить свої зміни:
```bash
git add js/pricing.js
git commit -m "feat(pricing): додано знижку 15% для замовлень від 3 квитків"
git push -u origin feature/zhe-bulk-discount
```

---

#### Крок 3. Виникнення конфлікту при спробі злиття
Же намагається влити зміни з оновленого `develop` у свою гілку, щоб підготувати PR:
```bash
git checkout feature/zhe-bulk-discount
git merge develop
```
👉 **Git зупиняє операцію та виводить повідомлення про конфлікт:**
```text
CONFLICT (content): Merge conflict in js/pricing.js
Automatic merge failed; fix conflicts and then commit the result.
```

---

#### Крок 4. Аналіз та вирішення конфлікту
Відкриваємо `js/pricing.js`. Git позначив конфліктний фрагмент спеціальними маркерами:

```javascript
<<<<<<< HEAD (Ваша гілка feature/zhe-bulk-discount)
  if (seats.length >= 3) {
    discountRate = 0.15; // Групова знижка 15% для компаній від 3 осіб (Же)
  }
=======
  if (hasVipSeats) {
    discountRate = 0.10; // Знижка 10% для поціновувачів комфорту (Ярік)
  }
>>>>>>> develop
```

**Рішення команди (комбінуємо обидві бізнес-фічі):**  
Замість вибору одного з варіантів, команда об'єднує обидва правила — надаючи знижку і для компаній, і для VIP:
```javascript
  // Об'єднана логіка після вирішення Merge Conflict:
  if (seats.length >= 3) {
    discountRate = 0.15; // Знижка для компаній (від Же)
  } else if (hasVipSeats) {
    discountRate = 0.10; // Знижка на VIP (від Яріка)
  }
```

---

#### Крок 5. Завершення злиття та фіксація:
```bash
# Додаємо вирішений файл до індексу
git add js/pricing.js

# Завершуємо коміт злиття
git commit -m "fix(merge): успішно вирішено конфлікт правил знижок у pricing.js"

# Відправляємо оновлену гілку на GitHub
git push origin feature/zhe-bulk-discount
```

Тепер на GitHub Pull Request показує статус **«Able to merge»** (зелена кнопка), і зміни успішно вливаються в `develop`.

---

## 🔍 5. Чек-ліст для проведення Pull Request:
1. **Зрозумілий заголовок** за стандартом `feat: ...`, `fix: ...`.
2. **Опис змін**: що саме було зроблено і які файли змінено.
3. **Самоперевірка**: чи відкривається `index.html` або `tests.html` без помилок у консолі (F12).
4. **Рев'ю**: обов'язково мінімум 1 схвалення (Approve) від іншого члена команди перед натисканням **Merge pull request**.
