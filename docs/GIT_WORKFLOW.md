# Регламент Git-Workflow та сценарій розв'язання конфлікту злиття

Лабораторна робота №2: Командна розробка додатків із використанням Git  
Проєкт: CineSphere

---

## 1. Модель розгалуження (Git Flow)

У проєкті застосовується розширена модель розгалуження Git Flow:

```text
main (виробнича релізна версія v1.0.0)
  │
develop (центральна інтеграційна гілка) ────────┬──────────────────┬───────────► [Реліз v1.0.0]
  │                                            │                  │
  ├── feature/zhe-catalog-ui ──────────────────┤ (Merge через PR) │
  ├── feature/yarik-booking-logic ─────────────┘                  │
  ├── feature/lyosha-hall-ui ─────────────────────────────────────┤ (Merge через PR)
  └── feature/illia-qa-tests ─────────────────────────────────────┘
```

Призначення гілок:
- `main` — захищена стабільна гілка. Містить перевірений релізний код. Прямі коміти заборонені.
- `develop` — основна гілка інтеграції напрацювань команди.
- `feature/*` — індивідуальні функціональні гілки розробників. Формат назви: `feature/<ім'я>-<назва_задачі>`.

---

## 2. Стандарт повідомлень комітів (Conventional Commits)

Всі коміти повинні відповідати загальноприйнятому стандарту:

| Префікс | Призначення | Приклад |
| :--- | :--- | :--- |
| `feat:` | Додавання нової функціональності | `feat(hall): додано неонове підсвічування обраних сидінь` |
| `fix:` | Виправлення помилки / дефекту | `fix(pricing): виправлено округлення суми зі студентською знижкою` |
| `test:` | Додавання або коригування тестів | `test(qa): додано автотест валідації номера телефону` |
| `docs:` | Оновлення документації | `docs: оновлено інструкції для команди у TEAM_PLAN_LR2.md` |
| `style:` | Форматування коду, відступи (без зміни логіки) | `style(css): оптимізовано медіа-запити для мобільних екранів` |
| `chore:` | Допоміжні зміни, конфігурація, інструменти | `chore: оновлено .gitignore` |

## 3. Базові операції Git для розробника

### 3.1. Оновлення develop та створення робочої гілки
```bash
# 1. Перехід у гілку develop
git checkout develop

# 2. Отримання актуального стану з віддаленого репозиторію
git pull origin develop

# 3. Створення функціональної гілки
git checkout -b feature/<ім'я>-<назва_задачі>
```

### 3.2. Фіксація та відправка змін
```bash
# 1. Перевірка статусу змінених файлів
git status

# 2. Додавання файлів до індексу
git add .

# 3. Створення коміту згідно з конвенцією
git commit -m "feat(ui): опис виконаної роботи"

# 4. Відправка гілки на GitHub
git push -u origin feature/<ім'я>-<назва_задачі>
```

## 4. Сценарій моделювання та розв'язання конфлікту злиття (Merge Conflict)

Вимогою лабораторної роботи є практична демонстрація виникнення та успішного розв'язання конфлікту злиття.

Місце виникнення конфлікту:  
Файл бізнес-логіки `js/pricing.js`, функція `calculateOrderTotal` (розрахунок підсумкової вартості замовлення зі знижками).

### 4.1. Етап 1: Внесення першої зміни (Ярік)
Ярік у гілці `feature/yarik-vip-discount` впроваджує знижку 10% для VIP-місць:
```javascript
// js/pricing.js у функції calculateOrderTotal
if (hasVipSeats) {
  discountRate = 0.10; // Знижка 10% на замовлення з VIP-місцями
}
```
Коміт та відправка змін:
```bash
git checkout -b feature/yarik-vip-discount
git add js/pricing.js
git commit -m "feat(pricing): додано знижку 10% на замовлення з VIP-місцями"
git push -u origin feature/yarik-vip-discount
```
Гілка зливається в `develop` через схвалений Pull Request.

---

### 4.2. Етап 2: Внесення паралельної зміни (Же)
Одночасно Же у гілці `feature/zhe-bulk-discount` змінює ті самі рядки, додаючи групову знижку 15% на замовлення від 3 квитків:
```javascript
// js/pricing.js у функції calculateOrderTotal
if (seats.length >= 3) {
  discountRate = 0.15; // Групова знижка 15% для компаній від 3 осіб
}
```
Коміт змін:
```bash
git add js/pricing.js
git commit -m "feat(pricing): додано знижку 15% для замовлень від 3 квитків"
git push -u origin feature/zhe-bulk-discount
```

---

### 4.3. Етап 3: Фіксація конфлікту при злитті
При спробі підтягнути оновлений `develop` у робочу гілку виникає конфлікт:
```bash
git checkout feature/zhe-bulk-discount
git merge develop
```
Повідомлення системи контролю версій:
```text
CONFLICT (content): Merge conflict in js/pricing.js
Automatic merge failed; fix conflicts and then commit the result.
```

---

### 4.4. Етап 4: Аналіз та розв'язання конфлікту
Конфліктний блок у файлі `js/pricing.js`:
```javascript
<<<<<<< HEAD (Поточна гілка)
  if (seats.length >= 3) {
    discountRate = 0.15; // Групова знижка 15% для компаній від 3 осіб
  }
=======
  if (hasVipSeats) {
    discountRate = 0.10; // Знижка 10% на VIP-місця
  }
>>>>>>> develop
```

Узгоджене рішення команди (інтеграція обох бізнес-правил через каскадну умову):
```javascript
  // Об'єднана логіка після розв'язання конфлікту:
  if (seats.length >= 3) {
    discountRate = 0.15; // Пріоритет групової знижки
  } else if (hasVipSeats && !promoCode) {
    discountRate = 0.10; // VIP-знижка за відсутності промокоду
  }
```

---

### 4.5. Етап 5: Завершення злиття
```bash
# Додавання виправленого файлу до індексу
git add js/pricing.js

# Створення коміту злиття
git commit -m "fix(merge): успішно вирішено конфлікт правил знижок у pricing.js"

# Відправка оновленої гілки
git push origin feature/zhe-bulk-discount
```

Після вирішення конфлікту Pull Request переходить у стан «Able to merge» і успішно зливається в `develop`.

---

## 5. Чек-ліст для проведення Pull Request

1. Зрозуміла назва за стандартом Conventional Commits (`feat: ...`, `fix: ...`).
2. Опис сутності внесених змін та перелік змінених модулів.
3. Обов'язкова перевірка відсутності регресій (проходження всіх автотестів).
4. Отримання мінімум одного підтвердження (Approve) перед виконанням операції злиття.
